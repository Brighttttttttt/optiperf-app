# Optiperf — instructions projet

App mobile-first de suivi d'entraînement coach ↔ athlète. Toute l'interface est en **français**. Thème « carnet d'entraînement » : tokens dans `src/app/globals.css`, signature visuelle = rampe RPE colorée (`src/lib/rpe.ts`).

## Commandes

- `npm run dev` — serveur de dev
- `npm test` — tests unitaires Vitest (`src/lib/*.test.ts`)
- `npm run test:e2e` — e2e de fumée, sans base (faire `npm run build` avant)
- `npm run test:e2e:auth` — parcours connectés contre une base réelle (base locale via la CLI Supabase en intégration continue). **Tout changement touchant au rendu d'une page authentifiée doit être couvert ici.**
- `npm run test:prod` — contrôle d'affichage dans un vrai navigateur contre le site en ligne, rejoué après chaque déploiement. Les tests locaux sont trop rapides pour reproduire les défauts liés au flux de rendu : ce contrôle est le seul à voir qu'une page répond correctement tout en n'affichant rien (incident #44).
- `npm run lint` et `npm run typecheck` — exigés par la CI
- `npm run smoke` — test de fumée contre la production déployée (routage CDN, en-têtes, POST des server actions) ; rejoué automatiquement après chaque déploiement
- `npm run seed` — données de démo (demande `SUPABASE_SECRET_KEY` dans `.env.local`)

## Architecture

- Next.js 16 App Router + Supabase (Postgres, Auth, Realtime, RLS). Le schéma et les politiques RLS vivent dans `supabase/migrations/` — toute évolution de schéma = nouveau fichier de migration numéroté, appliqué dans l'éditeur SQL Supabase.
- `src/lib/supabase/middleware.ts` est fragile par nature. Trois règles, chacune née d'un bug réel (couvertes par `e2e/session.spec.ts`) :
  1. ne rien insérer entre `createServerClient` et `getUser()` ;
  2. **toute réponse de redirection doit propager les cookies** de `supabaseResponse`, sinon la rotation du jeton se perd → boucle de redirections (visible surtout sur Safari) ;
  3. un compte authentifié **sans ligne dans `profiles`** doit être déconnecté, sinon le layout `(app)` (→ `/login`) et le proxy (→ `/`) se renvoient la balle à l'infini.
- `src/proxy.ts` protège les routes ; clients Supabase dans `src/lib/supabase/` (browser, server, middleware).
- Métriques d'entraînement (charge session-RPE de Foster, état ACWR, agrégation hebdomadaire `weeklySeries`) : fonctions pures dans `src/lib/metrics.ts`, couvertes par les tests — les modifier avec leurs tests.
- Graphiques (`TrendCharts`) : SVG écrit à la main, sans dépendance. Une seule teinte porte les données et un neutre porte le repère — l'identité vient de la **forme** (barre contre ligne), car deux verts proches échouent au seuil de distinction en vision normale. Tout graphique doit garder son tableau de chiffres : aucune valeur ne doit être accessible uniquement au survol.
- **Pas de `loading.tsx` ni de frontière `Suspense` sur une route entière** : celui de #36 laissait les pages définitivement sur leur squelette en production, l'échange de fin de flux ne se produisant pas (incident #44, retiré par #43). Les trois pistes de l'issue — CSP, réécriture par le proxy, `router.refresh()` du temps réel — ont été éliminées avec preuve sur un banc à latence réglable, sans que la cause soit identifiée : la voie reste fermée. Le retour visuel de navigation passe par `useLinkStatus` dans `Nav`, un état client posé après hydratation qui ne crée aucune frontière.
  - **Conséquence cachée** : Next saute le préchargement des routes dynamiques en l'absence de `loading.tsx`, et **toutes** nos routes sont dynamiques (elles dépendent de la session). Le `prefetch` des `<Link>` ne fait donc rien dans cette app — inutile d'y chercher un gain, ni de s'étonner qu'une navigation attende le serveur. Le forcer avec `prefetch={true}` ne changerait rien tant que `staleTimes.dynamic` vaut 0 s (défaut depuis Next 15) : le résultat préchargé est périmé en arrivant. Constat qui a fermé #41.
- **Mobile-first, mais plus seulement** (issue #65). La mise en page `(app)` est une colonne de téléphone jusqu'à `md`, puis une barre latérale (`Nav`, ex-`BottomNav`) plus un contenu borné à `max-w-4xl` : l'espace gagné sur grand écran sert aux **grilles** (dashboard coach en deux colonnes, athlètes × dates côte à côte dans `/planifier`), jamais à étaler une ligne de texte. Le retour visuel de navigation suit le bord par lequel l'onglet touche le contenu — au-dessus sur téléphone, à gauche en colonne.
  - `Nav` écrit ses deux mises en page dans des **variantes exclusives** (téléphone / ordinateur), jamais en surcharge de l'une par l'autre. La surcharge a produit un vrai défaut : deux positions déclarées au même palier, départagées par l'ordre d'émission de Tailwind — non par l'ordre d'écriture — et un décalage horizontal de téléphone jamais neutralisé, qui déportait la colonne (transparente sur grand écran) au milieu du contenu où elle absorbait les clics. Corollaire : Tailwind scanne le **texte brut**, y compris les commentaires et les fichiers Markdown — y écrire un nom de classe fait émettre la règle correspondante.
  - Le projet Playwright **`bureau`** (`e2e-bureau/`, 1440 × 900) est le seul à voir une régression de mise en page à la souris : tout le reste de la suite tourne en Pixel 7. Il tourne dans le même job que les parcours connectés, contre la même base.
- L'app est installable sur l'écran d'accueil : `src/app/manifest.ts`, icônes générées par `ImageResponse` (`icon.tsx`, `apple-icon.tsx`), métadonnées `appleWebApp` dans le layout. Ces routes **doivent rester hors du matcher du proxy** (`src/proxy.ts`) : le système d'exploitation les récupère sans cookie, et les protéger casserait l'installation. Vérifié par `e2e/installation.spec.ts` et le test de fumée.
- La fiche athlète charge une fenêtre large de séances (±8 semaines) pour que la vue semaine (`WeekPlanner`) navigue sans aller-retour serveur. Les helpers de semaine sont dans `src/lib/planning.ts`, testés.
  - `WeekPlanner` sert **les deux rôles** : le coach sur `/athletes/[id]/planning`, l'athlète sur `/planning`. `canPlan` (faux côté athlète) retire tout ce qui prescrit — les entrées vers `/planifier`, et surtout le lien « Modifier » vers `/seances/[id]`, qui ouvre le **formulaire de prescription** : un athlète y saisirait une modification que le trigger `enforce_session_ownership` refuserait à l'enregistrement. L'athlète déclare ses séances faites depuis l'accueil, pas depuis son planning.
  - Le contenu des séances affiché dans le panneau du jour (blocs et exercices) est chargé pour **toute la fenêtre**, pas pour la semaine visible : `chargerDetailsSeances` (`src/lib/session-details.ts`), en une passe par table plutôt qu'une requête par séance. Charger à la semaine rendrait un aller-retour serveur à chaque navigation, ce que cette vue évite délibérément.
  - **Déplacer une séance** (#85) se fait à la poignée, jamais en saisissant la carte entière : sur téléphone, saisir la carte empêcherait de faire défiler la page, et un appui long se confond avec la sélection de texte. Le geste est écrit en **événements de pointeur** (`setPointerCapture` + `document.elementFromPoint` sur les cellules `[data-jour]`) et non en glisser-déposer HTML5, qui ne se déclenche pas au doigt. Les flèches ← → sur la poignée font la même chose au clavier — et le focus doit être **rendu à la poignée** après coup, la carte changeant de place dans le panneau, sinon une seule flèche fonctionne. Trois gardes empêchent de déplacer un compte rendu : `peutDeplacer` à l'affichage, `.eq("status", "planned")` dans `moveSession`, et le trigger côté base.
  - L'état affiché vient de `planningState` (`src/lib/planning.ts`, testé) et non du seul `status` SQL : `planned` recouvre deux situations que l'athlète ne vit pas pareil — « À venir » et « À rattraper » (jour passé, aucun compte rendu). Le jour même compte comme à venir.
- Planification : un seul écran, `/planifier` (athlètes × dates en une fois), alimenté par `src/lib/planning.ts` (grille de dates, récapitulatif) et les modèles de `session_templates`. Il n'existe plus de formulaire par athlète — toute nouvelle entrée de planification doit pointer vers `/planifier`, éventuellement avec `?athlete=` ou `?depuis=`.
- Dates : toujours passer par `src/lib/dates.ts` — le fuseau Europe/Paris y est forcé car Vercel tourne en UTC. Ne jamais formater une date « à la main » côté serveur.
- Mutations : actions serveur dans `src/app/(auth)/actions.ts` et `src/app/(app)/actions.ts`.
- Liens d'email (confirmation, mot de passe) : l'inscription passe `emailRedirectTo` calculé depuis l'origine servie. `src/app/auth/callback/route.ts` traite les formes lisibles côté serveur (`?code=`, `?token_hash=`), puis relaie vers `src/app/auth/finaliser/page.tsx` pour le flux implicite, où les jetons arrivent dans le **fragment** (`#access_token=…`) que le navigateur n'envoie jamais au serveur. Tout `/auth/*` est public dans le proxy, sinon la confirmation serait interrompue avant de s'exécuter.

- **Région d'exécution** : `vercel.json` fixe `cdg1` (Paris), à côté de la base Supabase. Sans cela, Vercel exécute les fonctions à Washington et chaque requête traverse l'Atlantique — le dashboard passait de 630 ms à 1 500 ms. Ne pas retirer ce fichier, et vérifier `x-vercel-id` (attendu : `cdg1::cdg1::…`) si des lenteurs réapparaissent.
- L'utilisateur et son profil se lisent via `getSessionUser` / `getSessionProfile` (`src/lib/supabase/session.ts`), mémorisés par `cache()` : ne jamais rappeler `supabase.auth.getUser()` dans une page, la mise en page l'a déjà fait.
- Tâches de fond : elles vivent dans la base via `pg_cron` (migration 005), pas dans un cron d'hébergeur — cela évite d'y déployer la clé secrète et d'exposer une URL à protéger. Le planificateur tourne en UTC : toute tâche à heure locale fixe se déclenche sur les deux heures UTC possibles et vérifie l'heure de Paris à l'intérieur de la fonction.

## Workflow

GitHub Flow, protégé par ruleset : jamais de push direct sur `master`. Branche → PR → CI verte (lint, typecheck, unitaires, build, e2e) → merge squash. Vercel déploie une préversion par PR et la prod au merge.

Conventions détaillées dans `CONTRIBUTING.md`, vue d'ensemble dans `docs/architecture.md` — les deux sont à jour et font autorité sur ce point. L'essentiel :

- Le merge est un **squash** : le message du commit final est le **titre + la description de la PR**. C'est là que se joue la lisibilité de l'historique, pas dans les commits intermédiaires.
- Titre : impératif ou groupe nominal en français, sans préfixe technique (`feat:`, `fix:`), 70 caractères max.
- Description : le *quoi* se lit dans le diff, elle explique le **pourquoi** — avec la mesure ou le fait observé qui a motivé le changement, et ce qui a été écarté.
- Modèles d'issues et de PR dans `.github/` : les remplir plutôt que les vider.
- **Une migration ajoutée en PR n'est pas appliquée en production** : la CI la valide sur une base neuve, mais la pose reste manuelle dans le SQL Editor Supabase. Le signaler explicitement en fin de PR.

## Sécurité

- RLS sur toutes les tables ; les tests d'isolation comptent.
- **Deux verrous, pas un** : les droits SQL (migration 006) décident *quelles tables* un rôle peut ouvrir, la RLS décide *quelles lignes* il y voit. Supabase accorde automatiquement des droits à `anon` et `authenticated` sur toute table nouvellement créée — une nouvelle table doit donc déclarer les siens à la manière de 006, sinon le visiteur non connecté récupère un accès que seule la RLS retient.
  - **Même chose au niveau d'une colonne** : `profiles` restreint l'UPDATE aux seules colonnes qu'un athlète peut modifier (`grant update (col) on profiles`, migration 001, complété par 010 et 012) — un privilège par colonne, pas par table. Toute nouvelle colonne éditable sur `profiles` doit être ajoutée à ce grant dans sa propre migration ; sans quoi la RLS laisse passer une écriture que Postgres refuse quand même, en silence pour l'utilisateur (bug réel, rencontré deux fois de suite sur FC max/repos puis sur la VMA — un `update` qui ne renvoie qu'« Impossible d'enregistrer », sans indice sur la cause).
- Import d'un fichier de montre : **le fichier est lu par le navigateur** (`ImportActivityForm` → `src/lib/activites.ts`), jamais envoyé au serveur — un TCX de trail pèse 3 Mo, et l'athlète doit voir ce qui en a été tiré avant de valider. L'action serveur ne reçoit que les valeurs affichées, qu'elle borne : c'est son propre compte rendu, comme une séance saisie à la main. L'activité est insérée **avant** que la séance ne soit touchée, car c'est elle qui porte la contrainte d'unicité — un doublon doit être refusé sans avoir rien créé.
- `activities` (migration 007) porte ce qu'une montre a enregistré, avec un lien **facultatif** vers une séance : une activité peut n'être rattachée à rien, une séance en agréger plusieurs. L'anti-doublon est une contrainte SQL `unique (athlete_id, source, external_id)` — portée à l'athlète, car deux athlètes ayant couru ensemble déposent le même fichier. Lecture par l'athlète et son coach, **écriture par l'athlète seul** : c'est du compte rendu, même règle que ci-dessous.
- `activity_traces` (migration 009) porte la trace FC/allure/altitude d'une activité importée — une ligne **par activité** (quatre tableaux parallèles : `t_s`, `heart_rate`, `pace_sec_per_km`, `altitude_m`), pas une ligne par point : un trail de 2 h à la seconde dépasserait 7000 lignes pour une seule sortie. Sous-échantillonnée côté application (`MAX_POINTS_TRACE` dans `src/lib/activites.ts`, 400 points). Même visibilité que l'activité qu'elle accompagne (l'athlète et son coach), tranchée explicitement — 007 avait délibérément laissé cette question de côté en ne stockant aucune trace.
- `fc_max`/`fc_repos` (migration 010, sur `profiles`) servent de base au calcul des zones de fréquence cardiaque (`src/lib/zones.ts`, `ZoneBar`) ; saisis par l'athlète seul, le coach les consulte. `vma_kmh` et `personal_records` (migration 012) suivent une distinction plus fine : la VMA est saisie par l'athlète seul (même règle que FC max), mais un record personnel peut l'être par le coach aussi — RLS calquée sur `objectives`, pas sur `activities`. Deux champs voisins, deux règles différentes, chacune reprise du bon précédent.
- Séparation stricte prescription / compte rendu sur `sessions`, imposée par le trigger `enforce_session_ownership` (migration 002) : le coach ne modifie ni RPE, ni durée réelle, ni commentaire, ni statut ; l'athlète ne modifie pas la consigne d'une séance prescrite. Toute nouvelle colonne de `sessions` doit être classée d'un côté ou de l'autre dans ce trigger.
  - Cette séparation se joue **par séance et non par personne** (`v_is_athlete := old.athlete_id = v_uid`) — c'est ce qui a rendu le coach-athlète (#62) possible sans y toucher. Un même compte est l'athlète de ses propres séances et le coach de celles qu'il prescrit, avec des droits opposés sur les deux. Ne jamais y réintroduire de test sur `profiles.role`.
- **Rôle et mode d'affichage sont deux choses** (issue #62). Le `role` reste unique en base ; le **mode** (`src/lib/view-mode.ts`) décide de ce que l'app montre — un coach bascule entre « je coache » et « je m'entraîne » sans changer de compte. Le mode vit dans un cookie (`optiperf-vue`), pour survivre au rechargement.
  - Le cookie est une **préférence d'affichage, jamais un droit** : `resolveViewMode` le ramène au rôle pour un compte qui n'est pas coach, et l'action serveur relit le rôle en base avant de l'écrire. Un athlète qui le forgerait n'y gagnerait rien — la RLS ne lui montre aucun athlète.
  - Les pages qui distinguaient les deux publics branchent désormais sur le **mode** (accueil, réglages, `/planifier`, état vide des messages), plus sur `profile.role`. Deux exceptions volontaires : la suppression de compte (elle porte sur le compte, pas sur la vue) et le lien de retour d'une séance, qui se décide sur `profile.id === session.athlete_id` — le bon critère étant à qui appartient la séance.
- `workout_blocks` (migration 011) porte la structure d'une séance running (échauffement/intervalle/récupération/retour au calme), sur une table à part plutôt qu'en colonnes de `sessions` — la même séparation prescription/compte rendu que ci-dessus, mais reproduite en RLS puisqu'il n'y a pas de trigger sur cette table : qui prescrit écrit (le coach ou, pour une séance libre, l'athlète), et seulement tant que la séance reste `planned`. Comme ce statut change dans le temps, la policy interroge `sessions` en direct plutôt que de dupliquer une donnée qui se périmerait.
- Une séance de musculation structure ses exercices sur deux tables (migration 013), pas une comme le running : `exercises` (prescription, RLS calquée sur `workout_blocks` — qui prescrit écrit, tant que la séance reste `planned`) et `exercise_logs` (réalisé, `athlete_id` dénormalisé, RLS calquée sur `activities` — l'athlète seul écrit, à tout moment). Deux temporalités différentes justifient deux tables plutôt qu'une avec des colonnes des deux côtés : la prescription se fige, le compte rendu de l'athlète reste modifiable.
- Codes d'invitation : 10 caractères tirés d'un alphabet sans signes confondables (`generate_invite_code`, migration 004). Ils se lisent et se retapent à la main — ne pas rallonger sans repenser la saisie.
- Un compte ne peut pas envoyer plus de 20 messages par minute (trigger `enforce_message_rate_limit`). L'erreur remonte jusqu'au fil de discussion : toute nouvelle voie d'écriture doit afficher l'échec plutôt que l'avaler.
- Les limites de longueur sont doublées : contraintes SQL (migration 002) et constante `LIMITS` dans `src/lib/types.ts`, utilisée par les actions serveur et les `maxLength` des formulaires. Garder les deux synchronisées.
- En-têtes de sécurité (dont la CSP) dans `src/lib/security-headers.ts`, appliqués par le proxy et vérifiés par `e2e/headers.spec.ts`. Toute nouvelle origine appelée par le navigateur (analytics, CDN, stockage Supabase…) doit être ajoutée à la directive correspondante, sinon elle sera bloquée en production.
- Sur Vercel, un POST **sans** en-tête `Next-Action` vers une page prérendue (`/login`, `/signup`) répond 405 : c'est le CDN qui sert la page, comportement normal et non un bug. Les server actions du navigateur envoient cet en-tête et atteignent bien la fonction.
- `SUPABASE_SECRET_KEY` ne sert qu'aux scripts locaux (seed) — jamais côté client, jamais sur Vercel, jamais commitée (`.env.local` est ignoré par git).
